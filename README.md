# WC 翻译准备工作台

项目统一使用翻译准备工作台，支持英语→德语、简体中文→美式英语（en-US），提供项目、资料库、批次、六节点流水线、逐节点确认、失败重试、产物下载，状态落盘在 `workspace/pipeline/`。平台生成翻译前 ready 文件，译文仍由通用 Agent 按提示词完成。

## 启动

首次克隆后，在项目目录创建 Python 3.10+ 虚拟环境并安装依赖：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp -n config/config.example.json config/config.json
```

编辑本地 `config/config.json`，分别填写 `llm`、`embedding`、`rerank` 的完整接口地址 `api_url`、密钥 `api_key` 和模型标识 `model_name`。`llm` 使用兼容 Chat Completions 的 JSON 接口；向量和重排接口需符合对应节点的请求与响应格式。`vision` 默认继承 `llm`，可独立覆盖接口、密钥和模型，须支持图片输入。模板中的空值不会调用模型；已有本地配置无需重新复制。

仓库包含代码、提示词、规则与测试；真实 API 配置、客户资料、批次产物和向量缓存留在本地。换电脑后需重新配置模型，并在资料库页面上传所需材料。

安装和配置完成后启动：

```bash
.venv/bin/python app.py
```

打开 **http://127.0.0.1:5001/pipeline**（`/` 也会跳到这里）。侧栏保留准备流程与资料库。标签空格清洗、译后质量检查及旧准备页面的路由、接口和静态资源已移除；旧地址返回 404。

已有项目继续读取 `workspace/pipeline/projects.json` 中的资料库。全新启动时会建立「听风城堡」项目，可从上级目录初始化游戏介绍和客户要求；术语库、TM 在资料库页上传，不再读取旧 uploads 知识库。分类规则位于 `profiles/game/wc_key_rules.json`。

## 使用流程

侧边栏标题下方的「新建项目」用于新建或切换项目，当前项目和语向显示在批次信息中；资料库页面可用蓝色「返回工作台」按钮返回。

1. 打开 `/pipeline`，拖入或点击选择 XLSX / CSV 待译文件。
2. **项目资料均为选填**，建议尽量上传完整资料，以提高翻译准确率。未上传术语库时跳过术语匹配和筛选，`生效术语` / `无效术语` 留空；未上传记忆库时跳过 TM 检索，`TM参考` 留空。跳过节点会生成兼容的中间产物并自动继续，页面标记“已跳过”，不要求人工确认。该规则直接适用于已有项目，无需重新创建。
3. 点「开始准备」。自动节点连续执行，需要判断的节点停在「待确认」。
4. 每个确认节点下方有「确认并继续」「重跑本步」「下载产物」。
5. 任一节点失败会保留前序产物，给「重试本步」「重试并继续」；重跑本步会作废下游。
6. 跑完后右上角「下载最终产物」拿到 `05-TM.xlsx`（源文件 + speaker/分类/Context/生效术语/无效术语/TM参考 等新增列），下载文件名为「上传文件名_ready.xlsx」（替换原扩展名）。
7. 「准备自检」节点已暂时停用（`pipeline_service.PREFLIGHT_ENABLED = False`），不再作为一个确认步骤；`core_tools/preflight.py` 代码保留，需要时把开关改回 `True` 并重启即可恢复。
8. 顶栏「重置」现在打开确认面板：优先 **新建批次重跑**（保留旧批次和产物，基于同一源文件新建一个 0/6 批次），也可以 **清空当前批次**（删除 00-05，只留源文件，不可撤销）；不再使用浏览器原生 confirm。

非对白文件不需要 `speaker` 列。规范化仅在 Key 中实际识别到已配置的说话人时新增或补充该列；原文件已有的 `speaker`／说话人列与非空值保留，预览按实际产物显示。混合文件只给对白行填说话人，其他行留空。旧产物不会自动删列，需要从规范化重新运行或新建批次。

批次和项目都可以在左侧切换：批次下拉框切换历史批次，左上角项目名打开项目列表 / 新建项目。

已登记但文件丢失、上传文件损坏／语向错误、模型接口失败仍会报错，不会当作无资料跳过。后续补传库文件会用于之后运行的步骤；已有产物保留，请重跑相关步骤及下游或新建批次。旧项目如曾禁用 TM，重新上传有效记忆库即可启用。

## 中文到美式英语（2026-10-23）

新建项目选择“简体中文 → 美式英语（en-US）”。旧英德项目与新中英项目的资料库、批次分开保存；不在已有批次上切换语向。原有人物人设、人物关系和游戏介绍 MD 可全文复用，风格资料按本批及目标语言适用范围使用。

- 默认中文源文为 `game_text_cn`（兼容 `game_text_zh`、`zh`、`cn`、`source_text`、`中文`），英文目标为 `game_text_en`。同一角色存在多个候选列时，要求指定列映射，不猜列。
- 上传前可映射源文、目标、Key、note、说话人、情绪、气泡和 limit。原始表头、行位置、源文及已有目标值保留；缺目标列时补一列空白目标。映射随批次保存，新建批次重跑继承映射。
- 中文源文与情绪分开。中英只从 `animation`、`emotion`、`情绪` 或指定情绪列读取；英德仍兼容 `game_text_cn` 中的已知英文情绪标记。上传中文列全是情绪标记时明确报错。
- 中英术语库使用 `ZH,EN`（中文列也支持 CN/zh-CN/中文；英文列支持 EN/en-US/英文），CSV 使用 UTF-8。中文连续文本按最长候选匹配，混合英文保留边界，交给语境筛选排除假命中。
- 中英 TMX 接受简体中文 `zh`/`zh-CN`/`zh-Hans`/`zh-Hans-CN` 与 `en`/`en-US`，不把 en-GB 自动当美式英语。一个 TU 有多个适用语言变体时拒绝歧义。精确匹配优先，中文字符二元片段辅助 BM25；语义模型故障保持失败，不静默降级。
- 对白通读同组中文生成两段式中文 Context，只引用真实中文源文及人物资料，不使用已有英文译文。术语输出仍为 `生效术语` / `无效术语`；TM 输出为 `【中】` / `【英】`。
- 新批次内部记录统一使用 `source_text` / `target_text`；旧 Context 页面缓存仍能显示。Context 缓存包含语向与完整输入，TM 缓存包含语向、原文、库与模型版本；旧批次文件不自动改写。
- 翻译 Prompt 作为独立文件维护，不在平台管理或下载。平台只导出 ready；交给 Agent 时另行提供对应 Prompt、完整人设、人物关系、游戏介绍，非标准列映射也应告知 Agent。中英独立文件位于 `prompts/dist/zh-en-US/`，规则已包含适用客户要求。

命令行同样支持中译英，术语库与 TM 路径由本批提供：

```bash
.venv/bin/python pipeline.py 原始中文.xlsx --lang zh-en-US --termbase /绝对路径/中英术语.csv --tm /绝对路径/中英记忆库.tmx
# 暂无中英术语库及 TM 时可以直接运行；非标准列可指定：
.venv/bin/python pipeline.py 原始中文.xlsx --lang zh-en-US --source-column 中文台词 --target-column 英文稿 --emotion-column 表情
.venv/bin/python prompts/build.py --lang zh-en-US
```

验证使用本地测试数据和模拟模型响应，覆盖四类文本、中文分组及证据校验、术语边界、中英 TM 解析、语向缓存隔离、两库可选的四种组合、跳过节点自动继续、字段映射保存／重跑和原始数据保留。真实客户中文批次的模型判断、TM 召回质量和译文质量仍需用实际材料验收。

## 语向配置与扩展

网页、命令行、处理节点及 Prompt 生成脚本共用 `profiles/language/` 下的配置。当前正式登记的语言对仍为 `en-de` 和 `zh-en-US`；不会自动开放所有源语言与目标语言的组合。

- `_catalog.json`：源语言、目标语言的可复用规则，以及默认语向。源语言负责读取列、术语匹配、检索切分、否定提示及旧表情绪兼容；目标语言负责目标列、术语列、TM 语言代码及目标语术语规则。
- `<语向>.json`：登记一个明确支持的语言对、可选的默认列映射、命令行默认术语／TM 路径及 Prompt 源目录／输出目录。网页仍使用各项目上传的资料，配置中的库路径只作为命令行默认值。
- `core_tools/language.py`：统一加载并校验上述配置。网页通过 bootstrap 获取语言对选项；命令行 `--lang` 与 `prompts/build.py --lang` 使用同一清单。未知语向、歧义别名、无效策略或缺少 Prompt 源文件会明确报错。

增加语向的步骤：

1. 确定源语言、目标语言及地区版本，准备真实源表和适用客户规则。术语／TM 可选，但使用时必须属于该语向。
2. 在 `_catalog.json` 中补充缺少的源／目标定义；已有定义直接复用。`aliases` 用于语向选择，`columns` 用于正文列，`term_columns` 用于术语库表头。`tm_codes` 精确列出接受的代码，`tm_prefixes` 只在确实允许整个语言家族时配置，例如美式英语目标不使用 `en` 前缀接受 en-GB。
3. 准备该语向的 `base.md` 和四类 `scenes/*.md`，然后添加语向 JSON。`prompt_source`、`prompt_output` 均相对 `prompts/`，输出不能覆盖场景源文件。例如，未来登记中→德可复用 `zh-CN` 源规则和 `de` 目标规则，但仍需准备对应翻译 Prompt，不能直接指向中→英模板。
4. 运行 `prompts/build.py --lang <语向>`，补充该语向的真实样例测试并回归现有语向。停止正在执行的批次后重启工作台，核对页面选项、列映射、六步产物、缓存隔离和 Agent 翻译效果。

当前源语言策略为 `english`（词边界、已知英文复数扩展）、`han`（汉字连续匹配、字符二元片段检索、逐字符差异）和 `words`（按词匹配与检索、不扩展英文复数）。新源语言不适合这些策略时，须先补充相应处理与测试，不能仅填写语言代码。否定表达规则、停用词和 BM25 启用阈值随源语言配置；特定剧情的跨段线索仍属于项目规则，未知源语的线索词不会回退为英语。

语言规则变化会使相关 Context／TM 缓存失效；原 ready 与旧批次不会自动重写，需重跑相关节点。旧批次未保存语言字段时按所属项目解释。维护配置时应保留已有项目使用的语向，避免历史项目无法继续处理。

新语向与 Prompt 目录、模型真实效果是不同的验收项。自动化测试中的临时 `zh-de` 仅验证配置扩展和目标规则选择，没有登记到实际平台，也不表示已完成中德语言质量验收。

## 六节点

| # | 节点 | 来源 | 是否确认 |
|---|---|---|---|
| 00 | 规范化 | `core_tools/normalizer.py` | 自动 |
| 01 | 分类 | `core_tools/key_classifier.py` | 自动 |
| 02 | 上下文 | `core_tools/context_processor.py` + `core_tools/dialogue_context.py`（活动对白 LLM） | 需确认 |
| 03 | 术语 | `core_tools/term_scanner.py` | 自动 |
| 04 | 术语筛选 | `core_tools/term_filter.py`（LLM） | 需确认 |
| 05 | TM 参考 | `core_tools/tm_matcher.py` + `core_tools/tm_semantic.py` | 需确认 |

`06 准备自检` 目前不在流程里；代码和九条断言保留在 `core_tools/preflight.py`，由 `pipeline_service.PREFLIGHT_ENABLED` 控制是否挂回流程。

资料库里的游戏背景、人物人设、人物关系和风格指南会全文作为术语筛选的参考语境，不再截取前 1000 字符；术语库和记忆库直接决定第 03/05 步的数据。

「人物人设」与「人物关系」是两个独立上传入口，分别支持 UTF-8 `.md` / `.txt` 文件，可单独替换和移除。每个入口对应一份文档，可在文档内部按角色组织。旧版「人设 / 关系」合并文件原样保留在「人物人设」入口并显示待拆分提示；用户上传新的人设文件后提示消失，「人物关系」需单独上传。升级不自动拆写文件，不改现有批次产物。

对白支持客户的 `note = 完整 Key、key = 说话人` 格式：上下文和术语筛选读取同一身份信息，按活动、段号分组、句号数字排序，原始 `note`、`key` 和已有译文均保留。缺完整 Key 时不猜分段。更新后旧批次需重跑上下文及下游；若旧源文件丢失 `note`，应使用客户原始文件新建批次。

## 多证据分类与有边界的 Context（2026-10-29）

第 01 步汇总 Key、源文文本特征、说话人、连续格式区块和同区块明确分类的记录。`layout_segmenter.py` 比较 Key、源文、目标文及备注列的填充、上下边框、加粗／下划线，记录合并区域和图片锚点；多列变化才产生样式分界，单个无关单元格变色不会切块。空行、合并边界与明确的活动切换也会分区，重复颜色不代表同一活动。CSV 不提供样式证据。

分类优先级为人工覆盖、明确 Key 规则、辅助证据。`confirmed` 自动通过；`inferred` 和 `pending` 停在分类节点逐行确认。无 Key 不再默认归入 UI：仅在格式区块内有至少两条一致的明确分类、活动唯一且文本特征相符时推断。文本特征目前为本地的指令词与短名称规则，不是模型语义判定。分值是未校准的内部排序指标，不是准确概率。

分类面板优先展示影响下一步的记录：黄色待选择、绿色已选择但未提交、红色源文异常。已明确分类的记录默认折叠。用户可连续选择所有类别，再点一次「确认并继续」统一保存并自动生成 Context；单次选择不会请求接口或刷新页面。页内切换视图及请求失败会保留选择，同批次源文身份变化时清除失效选择；切换批次或手动刷新整个浏览器页面会清空未提交选择。原文为空或为公式时须先修正文件，不能仅靠指定类别放行。

已确认记录也可展开修改，清除人工覆盖同样先暂存，统一提交后重新判断。覆盖仅保存在当前批次 `classification_overrides.json`，绑定工作表、行及源文身份摘要，不改客户原文。提交后分类结果重新校验一次，仍有冲突时留在分类节点并高亮，否则直接进入 Context；后续术语和 TM 通过原有确认流程继续。未解决分类不能通过重跑／重试下游绕过。CLI 遇到需要确认的分类会停止，退出码为 3；可核对分类元数据后用记录 ID、`category`、`record_hash` 填写当前 CLI 批次的覆盖 JSON，再重跑分类。

ready 只增加既有的「分类」「Context」列；分类状态、依据、置信度、区块、人工覆盖保存在 `01-分类.classification.json`。第 02 步为非对白记录生成「活动背景／当前文本功能／关联对象」，存在可靠图片才加入图片证据，存在缺项才加入不确定项：

- 活动 UI：同活动、同功能单元关联，必要时补同活动标题和介绍；无 Key 只接受已确认且归属唯一的连续区块。
- 集卡：限定本活动本套组，带套组名、同套卡片及明确的活动主题。缺卡片序号时不补造。
- 装饰物：按活动和物件编号关联对白；缺对应对白时仅引用活动介绍，不把邻近对白或图片当作该物件事实。
- 图片：使用实际锚点覆盖范围，区分活动级、套组级、唯一物件级。无明确范围、跨对象或覆盖待确认记录的图片不作为确定证据。工作台对归属可靠的图片调用视觉模型，补充主体、位置、清晰文字和不确定项；原图和锚点保留，不自动裁切或重新分配 Key。

每条关系的真实记录 ID、对象 ID、图片锚点、依据和不确定项保存到 `02-上下文.context.json`，可在 Context 页面展开查看。只改人工类别不足以证明活动或物件归属，缺可靠关系仍会留空待确认。对白继续沿用下面的整段场景分析。

人工分类修改会清除旧 Context、场景缓存及下游产物。新版批次保存输入、规则代码、语向规则、人工覆盖与项目资料摘要；再次读取批次时若依据变化，就作废相应节点及下游，等待重跑。第一次升级的旧批次尚无这套摘要，需从分类节点重跑；原先已经下载的文件不会自动改变。重置批次会删除分析缓存与中间结果，保留当前批次的人工覆盖；新建批次不继承覆盖。

固定客户样本断言在 `tests/fixtures/wc_classification_expected.json`，绑定原始文件 SHA-256，行号仅用于测试。第 30–31 行实际为集卡活动标题与介绍；卡牌从第 34 行开始。第 28、29、184、185 行缺少可靠 Key，预期保留待确认。客户 Excel 不随仓库分发，缺材料时这一条本地验收测试跳过。

### 活动对白场景分析

第 02 步只为「活动对白」生成场景分析。按完整 Key 分组、按数字句序通读该组全部已提供源文，并全文传入当前项目的人物人设、人物关系、游戏背景与风格资料，不摘要或截断人物原文。模型只选用与本组参与者、明确提及对象及当前剧情相关的信息；同一内容同时上传到多个入口时合并传入一次，并提示不能视为多份独立证据。

每组分析一次，向本组各行写入相同的中文 Context：

```text
【场景结构】
参与者、对白或独白的组织方式、明确的交流媒介与段内切换。

【情境与基调】
本段事件与发展、情绪和语气变化、需要保留的幽默、反讽、双关或线索。
```

当前源文决定剧情事实，人物背景帮助理解语气与关系，不把后续剧情提前写进台词。情绪 `thinking` 或角色后缀 `_remote` 不单独证明内心独白，气泡字段缺失时不默认媒介。其他语种附录不自动成为当前目标语规则。人物资料冲突、缺句或关键字段缺失时保留必要的不确定性。

预览按组展示完整结果，可展开同组源文、已核验的关联名称／跨段线索、模型引用的对白和人物资料原文。对白引用须为源文中的连续片段；人物资料引用允许忽略 Markdown 行引用符、行内代码、加粗标记及排版空白，文字本身仍必须连续匹配，不能改写。语义解释仍需在本步人工确认。表格只写原有 `Context` 列，原文、已有译文与其他字段保持；UI、集卡和装饰物仍使用原文关联方式。现有术语筛选继续读取本行 Context。

场景分析沿用 `config/config.json` 的 `llm` 配置，临时网络、限流及服务端错误最多尝试 3 次。无可靠分组、同段源文异常、分类冲突或完整 Key 重复时留空待确认；模型失败、输出格式或引用异常时本步失败，不发布本次不完整结果。通过校验的场景保存在批次的 `context_scenes/`，重试时复用相同输入的成功结果；缓存绑定全部资料、对白、提示词、模型和接口，任一变化都会重新分析。失败响应单独保存供诊断，只有重新通过全部校验后才能复用。选择「重跑本步」则清空本步场景缓存和旧 Context，重新分析；下游产物作废，规范化与分类结果保留。纯非对白批次不调用场景模型。

旧批次不会自动调用模型重算。首次升级请重跑分类及下游，或复制批次保留原产物再运行。底层 `ContextProcessor.process` 保留原关联模式，工作台和命令行适配器显式启用场景分析；人物资料由工作台当前项目资料库传入。

## TM 语义匹配（2026-10-22）

### 模型并发与图片视觉语义（2026-10-29）

`llm`、`embedding`、`rerank`、`vision` 的 `max_workers` 默认及上限均为 30。TM 的向量批次和重排请求、术语筛选、独立对白场景、独立图片均可并发。服务进程按接口提供方和模型共享 30 个请求槽：同模型跨批次／节点共用，不同模型独立，重试等待不占槽。调高并发不改变服务商限流或保证速度倍增；本服务仍限单进程部署。

首次上传界面的「文件列映射」默认收起，标准表头可直接上传；需要自定义时展开填写，收起不会清空已填值。

第 02 步将归属可靠的嵌入图片通过 Base64 图片输入发送到 `vision` 配置的模型；未配置独立接口时使用 `llm`。不发送已有目标译文。API 副本最长边限制为 2048 像素，原表图片字节和锚点不变。请求格式参照 [OpenRouter 图片输入文档](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding)。

视觉结果写入 `Context` 的「图片证据」，并在逐行关系详情中保留图片 SHA-256、模型、可见物体与位置、清晰文字、不确定项。结果标为模型观察，需对照原图核对；格式校验不能证明视觉事实准确。活动图不自动变成单个物件证据，拼图不按卡片 Key 猜对应关系；归属不明的图片不发送模型。

同一图片内容与使用范围在一次运行中只识别一次。成功结果缓存到批次 `context_images/`，绑定图片内容、范围、提示词、模型、接口与版本。临时失败最多尝试 3 次，明确失败或响应不合格时不导出本次不完整结果；重试复用已成功的图片与场景。主动「重跑上下文」会清空两类分析缓存，分类变更和重置也会使其失效。无图片的批次不会调用视觉模型。底层 `ContextProcessor.process` 默认关闭视觉调用，工作台和 CLI 适配器显式开启。

验证边界：本地并发与缓存逻辑由测试覆盖；当前 Gemini 接口已用不含客户内容的几何测试图验证图片输入和缓存。尚未进行真实客户图片的外部模型验收，也未进行真实 30 路接口压测。

第 05 节点保留原文完全一致和正文一致的优先通道；其余句子使用源文本身进行语义向量与 BM25 关键词混合召回，再调用重排模型。沿用 RO 的默认权重：70% 向量 + 30% 关键词；BM25 启用阈值由源语言配置，当前英语最高分须大于 5，中文须大于 0。默认召回 30 条，重排分数至少 0.65，最多选择 5 条历史原文。分数不是翻译正确率。历史原文存在多个目标语版本时保留全部版本并提示冲突，所以参考条目可能超过 5 条。

使用 `config/config.json` 现有的 `embedding` 和 `rerank` 配置（各自的 `api_url`、`api_key`、`model_name`）；`embedding` 可配置 `batch_size`、`max_workers`、`timeout`，`rerank` 可配置 `recall_k`、`final_k`、`threshold`、`max_workers`、`timeout`、`request_retries`、`retry_backoff`。无须另传 NPY。配置完整仅表示可以发起请求，不保证外部接口可用。

首次处理非精确命中的句子时自动生成记忆库向量；后续复用 `workspace/pipeline/tm_cache/` 中的缓存（命令行默认 `workspace/tm_cache/`）。缓存绑定语向及语言规则、TMX 内容、源文顺序、向量模型、接口和处理版本，修改任一项会重建，不复用 RO 向量或旧上传目录。上传 TMX 只校验语料，不立即调用模型。全为精确命中的批次无需模型请求。

输出仍是一个 `TM参考` 列和原有 `_ready.xlsx` 文件。参考保留原始英德文本、标签和参数，并提示数字、否定、参数或格式差异；不会回填目标译文。当前与 RO 一样，只用源句匹配，Context、分类、术语不参与重排，交给后续翻译环节结合判断。

临时网络错误最多尝试 3 次，响应漏项、零向量、维度不一致等会明确失败，不用空参考冒充未命中，不导出本次不完整结果。重试会复用已完成的整库向量缓存，查询向量和重排重新执行；尚未实现逐行恢复。重跑 TM 本步会清除旧的第 05 步产物，避免失败时下载到旧 ready；第 00–04 步保留。更新服务后，可从已完成批次的 TM 节点选择「重跑本步」应用新匹配。

## 下载排查

- 下载不会弹「另存为」框，文件直接进浏览器下载目录；先看 Downloads。
- 优先用阶段面板右上角的「下载产物」，它始终在可视区；底部的「下载产物」在长面板里可能被滚出视口。
- 如果浏览器或内嵌预览拦截下载，点旁边的「复制链接」，把地址粘贴到独立浏览器的新标签页打开。
- 页面已返回 `Cache-Control: no-store`；如果界面像旧版，用 `http://127.0.0.1:5001/pipeline?v=2` 或硬刷新。

## 当前限制

- 当前正式支持 WC 的 **en → de** 与 **zh-CN → en-US**；新语向需登记配置、准备 Prompt 并验证，不能仅换上传文件。项目创建后语向固定。
- 主工作台负责翻译前准备，生成 ready 文件供外部工具翻译；译后处理由外部流程完成。
- 单机单用户，无登录；后台任务在 Flask 进程内跑，不要用多 worker 部署。
- 活动对白场景分析与术语筛选需要 `config/config.json` 里有效的 `llm` 配置；没有配置时对应节点会失败并给出提示。
- TM 的非精确匹配需要有效的向量和重排模型配置；首次生成整库向量会耗时并产生接口费用。
- 准备自检暂时停用；恢复后它的“长度余量”按源文达到 limit 的 85% 计为告警，阈值在 `core_tools/preflight.py` 顶部。
